# 37.7.1 candidate: district payment providers

Builds on 37.7.0 (PR #60, merged). The commerce choice moves to each
district. Details: `docs/COMMERCE-PROVIDERS.md`.

- **Per-district choice**, stored in the database (migration
  `066_commerce_district_providers.sql`):
  - `commerce_provider_accounts`: PayPal, Square, BTCPay; test or live mode;
    credentials sealed with `COMMERCE_SECRETS_KEY` (AES-256-GCM), write-only.
  - `commerce_payment_setup`: which options families see, the default, and who
    processes cards. Default is nothing offered.
  - RLS by district; only the superintendent and district IT (`commerce:providers`)
    can read or change accounts. Every save and test is audited (field names only).
- **Quick-setup cards** on a new web screen, Payment options: PayPal,
  Visa/Mastercard, Square, Bitcoin, Venmo, Cash App, plus the sandbox. Each has
  official links (all checked 2026-11-17), credential fields, Test connection
  and a status.
- **Adapters**: PayPal (Orders v2), Square (Checkout API payment links; cards
  and Cash App Pay), BTCPay Server (Greenfield invoices; manual dollar
  refunds). Venmo and cards-through-PayPal: saved but "adapter coming";
  checkout refuses them. Webhook signature checks are written; no webhook
  endpoint yet.
- **Live gate**: `COMMERCE_LIVE_PAYMENTS_ENABLED=false` by default; live also
  needs live credentials. `COMMERCE_PAYMENT_PROVIDER` is removed.
- Families pick "Pay with" on web and Flutter, go to the processor's page,
  and come back to confirm.
- Tests: `test/commerce-providers-37.7.1.test.js`,
  `test/integration/commerce-providers.test.js` (mocked processors, no
  network), updated 37.7.0 tests, browser smoke, Flutter.
- The open FCM device push PR (#52) must now renumber past 066.
